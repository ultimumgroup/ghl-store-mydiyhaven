# GHL-only checkout: local v3 endpoint audit and proposed implementation

Research date: September 8, 2026, America/Chicago. This follow-up uses the **local GHL Toolkit**, not online documentation. Its catalog was generated July 20, 2026; relevant pages say v3 and were scraped July 17. The audit covers **630 endpoint entries and 79 webhook entries**. Snapshot age limits any conclusion about subsequently added endpoints.

## Recommendation and correction to the first assessment

**Try GHL's `POST /invoices/text2pay` first.** It is a materially better candidate than the first report established: the request accepts an array of products/prices/quantities, has `action: draft | send`, accepts an existing invoice `id` for updates, and explicitly returns `invoiceUrl`. The docs call that URL a **preview URL**, so a payable hosted checkout is still a test gate, not something established by the schema alone. [Local Create & Send reference](../../ultimum-ghl-master-toolkit/api-docs/ghl/invoices/text-2-pay-invoice.md)

The user is missing **invoice permissions**, not an identified general-purpose order-creation permission. The selected PIT does not include `invoices.readonly` or `invoices.write`; a v3 read of invoice settings returned 401. Add those for the invoice experiment. Add `contacts.write` and preferably `contacts.readonly` for guest identity and lookup, unless an existing trusted contact ID is supplied by another authorized server workflow. A configured authorized GHL `userId` is required for invoice generation; it is a separate identifier from the location. `users.readonly` is optional if we need API discovery rather than configuring that ID.

The earlier statement that payment remains unresolved was correct about the running implementation, but the invoice/payment-link design space was underexplored. The new preferred next step is a **test-mode invoice-backed checkout**, before Stripe or Supabase.

## Endpoint findings

| Mechanism | What the local catalog establishes | Consequence |
| --- | --- | --- |
| `POST /invoices/text2pay` | Create/update invoice; draft/send; productId, priceId, qty, amount; returns invoice plus invoiceUrl | Best dynamic-cart hosted-payment candidate |
| `POST /invoices/` | Create draft invoice with line items; response lacks a documented invoiceUrl | Usable staging alternative, but weaker direct handoff contract |
| `POST /invoices/:invoiceId/send` | `action: send_manually` is explicitly supported, alongside email/SMS actions | Candidate for publishing a draft without automatic outbound messaging; test status and URL behavior |
| `PUT /invoices/:invoiceId` | Update invoice | Cart revision before payment; do not overwrite a paid/processing invoice |
| `GET /invoices/:invoiceId`, `GET /invoices/` | Read status, amounts and line items | Reconcile paid/partial/processing/void states and recover invoice references |
| `POST /store/shipping-zone/shipping-rates` | Calculate rates using destination, amount, weight and products | We may reuse GHL shipping rules; POST here is a calculation, not order creation |
| `GET /payments/orders`, `GET /payments/orders/:orderId` | Read existing orders | No corresponding collection-level create-order entry found |
| `POST /payments/orders/:orderId/fulfillments` | Create fulfillment for an existing order; uses `payments/orders.write` | Explains a documented use of that scope; does not create the order |
| `POST /payments/orders/:orderId/record-payment` | Record manual payment | Only after independently verified external payment, if reconciliation requires it; never a card-charge substitute |
| Custom-provider endpoints | Register/connect a payment provider with paymentsUrl/queryUrl | Extension of GHL's payment experience, not a general headless cart/order API |
| Forms/funnels | Form lists/submissions/file uploads and funnel page listings | No documented general cart injection or arbitrary payment-form submission endpoint found |

[Machine-readable audit](checkout-endpoint-audit.json) contains source filenames, endpoint paths, scopes and webhook entries. [Audit script](../scripts/audit-checkout-catalog.py) reproduces the selection. It finds no endpoint paths containing checkout/cart/payment-link and no `POST /payments/orders`. This is a bounded catalog finding, not proof no private route exists.

There is a trap in the filenames: `saas/generate-payment-link.md` actually documents `PUT /saas/update-saas-subscription/:locationId`, and its deprecated counterpart is also SaaS subscription update. Neither is a retail payment-link creation endpoint. Read the method, path and schema rather than the filename. ## Live read-only evidence with this PIT

[Probe results](checkout-capability-probe.json), generated by [the read-only script](../scripts/probe-checkout-capabilities.py):

- `Version: v3` returned 200 for products, sampled product prices, store settings, shipping zones, white-label providers and custom-provider config.
- Shipping origin contains a country, but the location returned **zero shipping zones and zero rates**. Configure actual delivery/pickup rules before showing a final checkout total; an empty result is not free shipping.
- Invoice settings returned **401**. No raw error body or credential was logged; missing invoice permission is consistent with the scope screenshot, though this response alone is not a complete authorization diagnosis.
- White-label providers returned zero. This endpoint lists Authorize.net/NMI-based white-label integrations; **it is not a Stripe connection-status endpoint**. An empty response says nothing definitive about Stripe connectivity.
- One product and its four price records contained no `prod_`, `price_` or `acct_` references. This is a sample, not an exhaustive Stripe mapping audit. The GHL IDs are not demonstrably reusable Stripe IDs.

These probes made GET requests only. No invoices, contacts, orders, payments or messages were created. The storefront's existing version header was not changed merely because these additional v3 reads passed.

## Option comparison

| Option | GHL ownership | Customer experience | Main gap / cost | Recommendation |
| --- | --- | --- | --- | --- |
| Dynamic invoice + hosted invoice URL | GHL catalog, contact, invoice, payment status | Custom cart then hosted payment page | Prove URL payability, publication, inventory and order semantics | **First experiment** |
| Native GHL store/order form handoff | Most native commerce behavior | Native checkout; possibly extra selection | Need a supported way to transfer exact multi-item cart | Parallel fallback investigation |
| Preconfigured payment form/link | Native hosted payment for configured offers | Good for a few fixed bundles | Arbitrary cart/variants not established; cannot trust amount query parameters | Suitable for fixed offers only after testing |
| GHL estimate → invoice | GHL quote/proof approval and invoice | Deliberate review then payment | Slower than instant checkout | Strong fit for custom pens, engraving and bespoke work |
| GHL custom-object cart + invoice | GHL stores draft cart and payment artifact | Cross-device recovery possible | Schema/plan availability, API latency and uniqueness semantics | Add when recovery/project state warrants it |
| Direct Stripe Checkout | GHL catalog; Stripe payment session | Hosted checkout with a precise cart | Separate credentials, mapping, webhook ledger, GHL reconciliation | Second-line fallback |

## Concrete invoice experiment

1. **Server quote:** Accept IDs and quantities only. Fetch current product publication, exact price, stock, tax category and shipping inputs. Calculate any price/discount from trusted records. Keep GHL productId and priceId on every invoice line and include the human-readable option name. Do not collapse everything into a synthetic one-off “cart total” product: that loses product reporting, stock identity and refund clarity.
2. **Identify checkout:** When the customer proceeds, obtain contact information, resolve/upsert the contact, and assign a random checkout ID plus cart revision. Do not overwrite an existing contact's unrelated fields or DND settings. Persist an invoice reference using the chosen staging design.
3. **Create the draft:** Use `POST /invoices/text2pay` with `action: draft`, `liveMode: false`, the configured userId and trusted line items. Its `sentTo` object is required and contains required `email`; contactDetails contains required nested identity fields when supplied. Test minimal valid inputs rather than inventing phone/email values. The documentation includes inconsistent generated examples, so schema validation in the sandbox is essential.
4. **Inspect the returned URL:** Open invoiceUrl in a fresh browser with no GHL login. Verify the exact variant, quantity, currency, amount and payment controls. Do not fabricate an invoice URL from its ID. Test custom-domain redirects and mobile behavior. Do not expose raw contact/invoice data through a public diagnostic page.
5. **Publish if necessary:** If draft URL is preview-only, test `POST /invoices/:invoiceId/send` with `action: send_manually`, `liveMode: false`, authorized userId, and automatic charging disabled. Revisit the returned/staged URL. Whether this permits payment without delivering a message is a **specific experiment**, not guaranteed by the action name. Do not use `send`, SMS or email actions just to obtain a URL.
6. **Complete a test payment:** Validate GHL invoice paid status and transaction evidence, native order creation (if any), variant IDs, actual inventory decrement, coupon accounting, taxes, shipping and fulfillment visibility. Inspect failure, cancellation, partial payment and asynchronous payment paths. A paid invoice does not by itself prove native-store order or inventory semantics.
7. **Confirm on our site:** A return URL/query parameter is not payment proof. Re-read authoritative status, match location/contact/reference/amount/currency/mode, and wait for settlement where needed. Clear the cart only for the matching completed checkout revision. If hosted return customization is unavailable, provide a “Check payment status” action when the customer returns to the preserved cart.
8. **Resolve race conditions:** Do not mutate an invoice already open for payment without a defined revision/expiry policy. If the cart changes, create a controlled new revision and invalidate the old payable document where supported. Test stale links, simultaneous tabs, double-clicks, timeouts and retry after an ambiguous create response.

The ready-to-review fixture [invoice checkout blueprint](invoice-checkout-blueprint.json) shows the draft and manual-publication payloads with fake placeholders. It is not connected to a live endpoint. Amount units must be confirmed at the invoice boundary with a known $9 item; do not infer units from the field name or silently reuse Stripe's minor-unit convention.

## Shipping, tax, discounts and inventory

The rate-calculation endpoint is a useful discovery but the local schema has contradictions: `amountAvailable` is typed as string with a country-code enum despite boolean-like prose; `products` is described as price IDs while its nested `id` description says product ID. Total weight is required in kilograms. These are reasons to run a narrow fixture comparison against native GHL checkout before implementing, not reasons to copy the misleading generated schema. [Local shipping calculation reference](../../ultimum-ghl-master-toolkit/api-docs/ghl/store/get-available-shipping-zones.md)

Start by configuring GHL shipping zones, then compare a known item/destination/weight and threshold in native checkout and the calculation API. Recompute server-side after address/cart changes. Empty rates block shipping or offer a separately configured pickup method. An invoice shipping charge may need a distinct trusted line item; prove how this affects tax and native reporting.

Invoices expose automaticTaxesEnabled and per-item automaticTaxCategoryId/manual taxes. That does not establish a complete standalone tax quote endpoint or that store tax settings automatically apply to an invoice. Verify the configured business/provider tax behavior and destination handling. Coupons likewise cannot be reduced safely to a percentage: eligibility, usage limits, date windows, product restrictions and atomic redemption matter. Mapping a coupon to an invoice discount may bypass usage accounting; keep codes disabled until tested.

Invoice price IDs preserve intent but do not establish stock reservation or decrement. Verify two competing checkouts for the last item and repeat webhook delivery. If invoices do not manage stock, using native checkout may be simpler than recreating concurrency-sensitive inventory updates. A non-atomic “read quantity then write quantity minus one” is not adequate across instances.

## Abandoned carts and staging without Supabase

A temporary native **order** is not the first staging object: no public create-order method was found. Separate browsing intent from an amount payable.

- **Phase 1, simplest:** Keep anonymous browsing in the current cookie. On checkout intent, stage one draft invoice and record its reference. GHL retains the product/price lines. Abandonment begins when the customer identifies themselves and starts checkout; anonymous carts remain browser-local.
- **Phase 2, sales follow-up:** A dedicated GHL opportunity pipeline can show Checkout started → Awaiting payment → Paid / Expired. Add checkout ID, invoice ID, cart revision and last activity as dedicated fields. Use known opportunity IDs for updates. Do not assume opportunity upsert is keyed by our checkout UUID, or that one opportunity per contact can represent multiple simultaneous carts. Requires opportunities permissions and configuration.
- **Phase 3, richer carts/projects:** A `custom_objects.store_checkout` record can hold a random checkout ID, revision, contact association, product/price/quantity lines (using supported field types), invoice reference, status and activity timestamp. This can later connect to custom proofs/projects. The API supports custom records and workflow integration, but plan availability, limits, field types, search and uniqueness must be verified. JSON-as-text is a possible encoding, not an assumed native field type. Requires schema provisioning and record read/write scopes. [Custom records](../../ultimum-ghl-master-toolkit/api-docs/ghl/objects/create-object-record.md)

Suggested state machine: `anonymous → identified → draft → awaiting_payment → processing → paid`, with `expired`, `cancelled` and `failed` branches. Only the matching paid revision suppresses follow-up and triggers fulfillment. A timer may classify an identified unpaid checkout as abandoned after a business-chosen delay, then recheck paid/processing status immediately before any recovery action. No recovery messages were sent or scheduled here.

GHL's native abandoned-checkout trigger must be tested with native checkout separately; an invoice/custom object does **not** automatically emit that event. Recovery can use configured GHL workflows, contact/pipeline changes, or a scheduled reconciliation worker. A PIT is not a webhook subscription. Marketplace InvoicePaid/InvoiceUpdate/InvoiceVoid events require app/webhook setup, or use a configured workflow webhook and validate its separate authentication contract. Polling GHL status is a viable small-store initial option. [InvoicePaid](../../ultimum-ghl-master-toolkit/api-docs/webhook/InvoicePaid.md)

GHL custom objects can store durable business state without Supabase, but the reviewed schema does not establish atomic uniqueness/idempotency or locking. A signed cookie protects a reference from tampering, not from duplicate requests across instances. If the deployment cannot provide a single durable serialized worker or a proven unique GHL record key, add a small transactional ledger/queue for checkout creation and callbacks. It can be SQLite on persistent single-host infrastructure or managed transactional storage; ephemeral AI Studio files are not assumed durable. This is operational state, not a second product catalog.

## Direct Stripe fallback, and the product-ID assumption

GHL using Stripe for payments does **not** establish that every GHL product/variant has an accessible reusable Stripe Product/Price in the account our credentials can access. The local product/price schemas do not expose a guaranteed Stripe mapping; the live sample exposed none. Imports, live/test modes, account ownership and connected-account context all need verification. Do not pass GHL IDs as Stripe price IDs.

A direct-Stripe design would keep the GHL catalog authoritative, build a server-side checkout session from freshly verified lines, and either use verified Stripe price mappings or create session-specific price data. For USD the Stripe integration must deliberately convert to integer minor units. Include GHL identifiers and a checkout reference in supported metadata; verify field/line limits against Stripe's SDK/API before implementing. We did not access Stripe credentials or independently audit Stripe documentation in this local-GHL-only pass, so this is an architecture proposal rather than a tested Stripe contract.

The payment callback needs signature verification, durable event deduplication, amount/currency/mode validation and a recoverable writeback process. Determine whether GHL automatically imports these externally initiated transactions; do not assume it does. If not, update a pre-existing GHL invoice with an independently verified external-payment record and provider reference where supported, or maintain the payment reference in a custom object/opportunity. Neither operation guarantees a native store order. Define refund, tax, stock and fulfillment ownership explicitly to prevent duplicated receipts, charges or decrements.

Prefer one-time Checkout Sessions for an arbitrary changing cart over creating permanent catalog products/payment links for every cart. Preconfigured links remain useful for a small set of fixed offers. Never create a shared “temporary cart product” and change its price between customers; that introduces cross-customer races and damages product reporting.
